# Security

Crimson Headless Passkey deliberately trades away some of what makes a passkey
strong. This page explains exactly what, how the tool limits the damage, and
what you need to do on your side.

## What Changes When You Use This

A normal passkey's private key never leaves your device's secure hardware, and
each use needs you to be there (Touch ID, a tap). Registration with this tool
enrolls an **additional** passkey whose private key is generated by Chrome's
virtual authenticator. On macOS that key is saved in your login Keychain by
default; elsewhere, or with `--secret-store file`, it is saved in
`passkey_credential.json`. It does not copy or weaken your existing passkey.

| Property | Real passkey | This tool's passkey |
|----------|--------------|---------------------|
| Origin binding (phishing resistance in the browser) | Yes | **Yes**: the browser still only lets the IdP's own origin request an assertion |
| Device binding (key can't be copied) | Yes | **No**: the key is stored data (a Keychain item or a file) that can be exported |
| User presence and verification (a human at the device) | Yes | **No**: the authenticator always reports the user as verified |

So **anyone who can read the private key can sign in as you, from any
machine, with no password and no prompt,** until you remove that passkey in
Okta. Because the authenticator claims user verification, that one key
usually satisfies the full MFA policy for every application behind the IdP.
Outside a browser, a stolen key can sign anything, and origin binding no longer
helps.

The saved session is a second secret: live cookies and local storage for the
IdP **and every site visited** during a saved sign-in, valid until those
sessions expire.

Treat both like an SSH private key with no passphrase.

## Where the Secrets Live

**By default on macOS, no secret is stored on disk.** The private key and the
saved session both live in your login Keychain, and the data directory keeps
only `passkey_credential.json` with non-secret fields and the sign counter.

| Secret store | Default on | Private key | Saved session | Use it for |
|--------------|-----------|-------------|---------------|------------|
| `keychain` | macOS | Login Keychain | Login Keychain | Your own Mac. Encrypted at rest and tied to your macOS login; backups, sync folders and copies of the data directory carry no secrets. |
| `file` | Linux, Windows | `passkey_credential.json`, `0600` | `auth_state.json`, `0600` | Fully hands-off runs where nobody is logged in: servers, CI. |

> [!WARNING]
> `--secret-store file` is **deliberately possible, but not the default, for
> security reasons.** It puts the passkey's private key and live session
> cookies in plain files. Anyone who gets a copy of those files (a backup, a
> sync folder, a stolen disk) can sign in as you. Use it only where nobody can
> be logged in to unlock a keychain, and protect the directory as described
> below.

The Keychain protects secrets **at rest**. It does not hide them from code
already running as you: the key is handed to Chrome in memory at every
sign-in, and the program that stored it can read it back without a prompt.

The login Keychain is unlocked while you are logged in, including when the
screen is locked, and locked when you log out. A scheduled sign-in (a
LaunchAgent or cron job at 3 a.m.) works while you stay logged in. On a
machine where nobody is logged in, use `--secret-store file`. Storing the
Keychain's password next to the job to unlock it would put a secret on disk
again, which defeats the point.

Switching stores is automatic: set `--secret-store` (or
`CRIMSON_HEADLESS_PASSKEY_SECRET_STORE`) and the next sign-in moves the key and
the session. Each move stores the secret in its new place before removing it
from the old one, so an interrupted move never loses it.

The keychain store also exists on Linux (GNOME Keyring or KWallet through the
Secret Service) and Windows (Credential Manager), but only in a logged-in
desktop session. A headless Linux server has no unlocked keyring, so use
`--secret-store file` there; that is already the default off macOS.

## HTTP Client Cookie Scope and Redirects

The in-memory ``httpx`` client (``session.http_client`` / ``http_client_from_cookies``):

- Builds the jar from ``http.cookiejar.Cookie`` objects and applies
  ``DefaultCookiePolicy(strict_ns_domain=DomainStrictNonDomain)`` so **host-only**
  cookies are never sent to subdomains. (httpx copies the jar on each
  ``build_request`` and drops the policy; the redirect guard recomputes the
  ``Cookie`` header from the policy-bearing client jar before every hop.)
- Follows redirects manually (``follow_redirects=False``, max 10). Before each
  hop: https only; default port (none/443); no userinfo; host is the site or a
  proper subdomain; never an **exact** IdP/SSO host.
- Rebuilds each hop with ``client.build_request`` so the jar computes cookies
  per URL (including ``Set-Cookie`` from the redirect response). Copied headers
  drop ``Cookie``; ``Authorization`` is dropped when the host changes.
- Suffix blocks (``.harvard.edu``, ``.okta.com``) apply only when **filtering
  cookies into the jar** (parent ``Domain=.harvard.edu``). Request targets like
  ``https://canvas.harvard.edu/`` are allowed.

## Cookie Export (`--cookies-out`)

By default, cookies never leave memory. `http_client()` builds an in-memory
`httpx` session for one site. IdP and SSO cookies are **always** excluded
(built-in Harvard / Okta / Microsoft hosts, `*.okta.com`, `*.harvard.edu`,
`login.live.com`, plus any configured hosts) unless you pass
`include_idp=True`. Configuration adds to that list; it never replaces it, and
`settings=None` still excludes the built-ins.

Redirects are followed manually (at most 10 hops). **Before** each hop is
sent, the URL must be https, on the site host or a proper subdomain (lookalike
hosts like `evilcontoso.sharepoint.com` are refused), and never an IdP/SSO
host. The response is closed before a refusal is raised. Cookies keep their
`Secure` and host-only scope via `http.cookiejar.Cookie`.

Writing cookies to disk needs the **explicit** flag `--cookies-out FILE` (or
`save_cookies()` in library code). The file is written through the same 0600
atomic path as the rest of the tool, holds only that site's cookies (IdP
filter applied again), refuses to overwrite an existing file unless `--force`,
and the tool prints a warning. Anyone who can read the file can act as you for
that site until the cookies expire. Prefer keeping cookies in memory.

## Per-user Config File (no secrets)

`~/.config/crimson-headless-passkey/config.toml` (or
`$CRIMSON_HEADLESS_PASSKEY_CONFIG` / `--config`) holds **non-secret settings
only**: username, UPN, hosts, defaults. It must not contain a key, cookie,
token or password. Keys or values that look secret are refused. The same
ownership rule as `.env` applies (you own it; nobody else can write it). Tests
always point this at a temp path via `CRIMSON_HEADLESS_PASSKEY_CONFIG`.

## Redaction

Errors, tracebacks, log records and stderr are scrubbed by `redact.py` before
they are shown. Known secrets (private key, credential IDs, cookie values
registered when loaded or exported, plus URL-encoded / base64 variants) and
secret-shaped strings (Cookie / Authorization headers, JWTs, PEM blocks, URL
query strings including `tempauth=`, long opaque base64) are replaced with
`[REDACTED]`.

At import, a `RedactingFilter` is attached to the `httpx`, `httpcore` and
`playwright` loggers so library/bot callers get scrubbing without calling
anything. For process-wide stderr and uncaught-traceback scrubbing, call
`redact.install()` or use `with redact.active():` (reference-counted so nested/concurrent `signed_in`/`fetch` calls do not uninstall early) (what `signed_in` and
`fetch` do automatically). See README.

Tests assert registered secrets are absent from `str(err)`, `repr(err)`, the
stderr wrapper, the excepthook, and log records. A separate test removes the
filter and asserts the secret then *appears*, so the absence assertions are
shown to be meaningful.

## What the Tool Protects Against

- **Other users on the machine.** Files are written `0600` through a temp file
  and an atomic rename, in a `0700` directory. Loading refuses files that are
  readable by others, not owned by you, symlinks or not regular files, and
  refuses directories others can write to.
- **Accidental commits.** Secrets live in `~/.local/share/crimson-headless-passkey/`,
  outside any repository. `.gitignore` also covers the file names and temp
  files, and the release package is built from an explicit file list.
- **Silent reuse after sign-in.** The virtual authenticator exists only during
  the sign-in itself and is removed before the page is handed back, so a later
  Okta step-up prompt in the same session is not approved silently.
- **Counter regressions.** The WebAuthn signature counter is saved after every
  run, only ever upward, and a lock stops two runs from presenting the same
  value.
- **Leaking tokens to logs.** Printed URLs have their query string and
  fragment removed (OAuth codes, tokens). Errors, tracebacks, log records
  and stderr run through `redact.py`. The private key and cookies are
  never printed.
- **A planted `.env`.** Settings files that someone else owns or can write to
  are refused, since they decide where the username goes and where the key is
  read from.
- **Typing the username in the wrong place.** The username is only filled into
  a page on a configured IdP host over https, and the submit is tied to that
  field's own form.
- **False "signed in" results.** Success needs an https destination plus
  evidence that a sign-in happened. Browser error pages never count.

## What It Does Not Protect Against

- **Malware or anyone running as your user.** File permissions don't stop
  them, and neither does the Keychain: the program that stored the key reads
  it back without a prompt.
- **Copies of the file you make or allow** (with `--secret-store file`):
  backups (Time Machine), cloud sync (iCloud Drive, Dropbox), shared or network
  home directories, dotfile repos. The session file is copied the same way
  with either store.
- **A stolen, unencrypted disk.** Use FileVault or an equivalent.
- **A compromised IdP origin.** While the tool runs, script on the IdP's own
  origin can get assertions without a prompt.
- **Debug output.** `DEBUG=pw:protocol`, Playwright traces and browsers with a
  remote-debugging port all expose the private key. The CLI warns when `DEBUG`
  enables protocol logging.
- **Windows.** Permission checks are POSIX-only. Windows is not supported.

## Protecting the Credential

- On macOS, keep the default keychain store. Use `--secret-store file` only on
  machines where nobody is logged in.
- Keep the data directory on a local, encrypted disk, under your home.
- Never point `CRIMSON_HEADLESS_PASSKEY_HOME` or `--data-dir` at a synced,
  shared or project directory.
- Exclude it from backups. On macOS:
  `tmutil addexclusion ~/.local/share/crimson-headless-passkey`
- **One passkey per machine or pipeline.** Register again on each machine
  instead of copying the file, so each one can be revoked on its own. Never
  share one file between people.
- In CI, use `--secret-store file`: store the file as a masked secret, write it
  `0600` at job start, and delete it at job end. Never run two jobs with the same credential at once.
- Never restore an old copy of the credential file: its counter is behind
  Okta's, which looks like a cloned authenticator.
- Name the authenticator in Okta (for example `headless - hostname - 2026-10`)
  if your Okta allows it, so you can tell it apart from your real passkeys.

## Rotating and Revoking

Deleting or replacing the file does **not** revoke anything: any copy of it
keeps working. To revoke:

1. In Okta, open your security settings and **remove** the "Security Key or
   Biometric" authenticator this tool registered.
2. Sign out of all sessions (Okta's "sign out everywhere", if your org offers
   it) to end any sessions in a leaked `auth_state.json`.
3. Delete the data directory:
   `rm -rf ~/.local/share/crimson-headless-passkey`, and with the keychain
   store its items. On macOS, repeat until it reports that none are left:
   `security delete-generic-password -s crimson-headless-passkey`
4. Register again if you still need automation.

Do this whenever a file may have been exposed, when you decommission a machine,
after `register --force`, and if Okta suddenly rejects the passkey (a counter
mismatch can mean someone else used a copy).

## Policy and Responsible Use

- Use this only for **your own accounts**, and only where your organization's
  authentication and acceptable-use policies allow automated MFA. Many
  institutions require MFA to involve a person. When in doubt, ask your
  security office first.
- Never enroll this tool on admin or shared accounts without the owner's and
  the security team's approval. Prefer a dedicated, least-privilege account
  for automation where your organization offers one.
- Harvard's IdP is only the default configuration. This project is not
  affiliated with, endorsed by or supported by Harvard University or Okta.
  Report problems with an IdP to that organization, not here.

## For Identity Provider Administrators

Enrollment shows up in the Okta System Log like any other "Security Key or
Biometric" enrollment. Chrome's virtual authenticator reports the fixed AAGUID
`01020304-0506-0708-0102-030405060708`, and when attestation is requested it
returns `packed` attestation signed by no vendor in the FIDO Metadata Service
(checked with Chrome 154, October 2026). An AAGUID allowlist **combined with**
required trusted attestation therefore blocks enrollment by this tool. An
AAGUID allowlist alone does not, since an unattested AAGUID is just a claim.
Verify the behavior in a test tenant before relying on it.

## Reporting a Vulnerability

Please report security problems privately through GitHub's
**Report a vulnerability** button on the repository's Security tab, not in a
public issue. Include the version (`crimson-headless-passkey --version`) and
steps to reproduce. **Never include a real credential file, cookies or
unredacted logs.** Expect an acknowledgment within a week.

Only the latest release receives fixes.
